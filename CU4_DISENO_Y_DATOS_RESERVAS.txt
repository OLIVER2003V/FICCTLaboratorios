1. DISENO LOGICO (MODELO CONCEPTUAL / RELACIONAL)
--------------------------------------------------------------------------------
El modulo de Reservas Extraordinarias y Notificaciones (CU4) administra las
solicitudes especiales de laboratorios realizadas por docentes o directores para
examenes, recuperaciones, practicas, eventos academicos y defensas de proyecto,
asi como el flujo de aprobacion/rechazo por el Encargado y la notificacion automatica.

A. ENTIDADES Y DEFINICION LOGICA:
  * RESERVA (id, laboratorio_id, solicitante_id, fecha, hora_inicio, hora_fin, tipo, motivo, estado, resuelto_por, observacion, creado_en)
    Registra la peticion de uso temporal de un laboratorio para una fecha y franja horaria determinada.

  * NOTIFICACION (id, usuario_id, asunto, cuerpo, reserva_id, enviado_en)
    Historial de mensajes y avisos emitidos hacia los solicitantes informando resoluciones o confirmaciones.

B. RELACIONES Y CARDINALIDADES:
  * LABORATORIO (1) ──── (N) RESERVA
    Un laboratorio alberga multiples reservas a lo largo del semestre ('laboratorio_id').
  * USUARIO [SOLICITANTE] (1) ──── (N) RESERVA
    Un docente o director puede realizar multiples solicitudes de reserva ('solicitante_id').
  * USUARIO [ENCARGADO] (1) ──── (N) RESERVA (Opcional / Nulo mientras este PENDIENTE)
    El encargado evalua y resuelve la solicitud aprobando o rechazando ('resuelto_por').
  * USUARIO (1) ──── (N) NOTIFICACION
    Cada notificacion tiene un usuario destinatario ('usuario_id').
  * RESERVA (1) ──── (N) NOTIFICACION (Opcional / ON UPDATE CASCADE ON DELETE SET NULL)
    Una reserva genera una o varias notificaciones de estado ('reserva_id').

C. REGLAS DE NEGOCIO E INTEGRIDAD:
  1. Restriccion de Fechas Futuras: Las reservas solo pueden solicitarse y aprobarse para fechas
     y horas estrictamente futuras respecto al momento de la operacion.
  2. Tipos de Reserva Permitidos: 'EXAMEN', 'RECUPERACION', 'PRACTICA', 'EVENTO',
     'DEFENSA DE PROYECTO', 'DEFENSA'.
  3. Ciclo de Vida: Inicia como 'PENDIENTE'. El Encargado puede cambiar a 'APROBADA' o 'RECHAZADA'.
     El solicitante puede pasarla a 'CANCELADA' antes de que ocurra.
  4. Control de Choques (Disponibilidad Estricta): No se permite aprobar una reserva si se superpone
     con una clase de carga horaria base (CU3), con otra reserva ya 'APROBADA' o con una fecha bloqueada (CU2).
  5. Coherencia de Horas: La hora de fin debe ser estrictamente posterior a la hora de inicio ('hora_fin > hora_inicio').
  6. Auditoria Obligatoria: Al aprobar o rechazar se registra el Encargado ('resuelto_por') y una observacion explicativa.

4. SCRIPT SQL COMPLETO (DDL Y DML)
--------------------------------------------------------------------------------
-- SCRIPT DDL: CREACION DE TABLAS (CU4)
CREATE TABLE reserva (
  id             SERIAL PRIMARY KEY,
  laboratorio_id INT  NOT NULL REFERENCES laboratorio(id),
  solicitante_id INT  NOT NULL REFERENCES usuario(id),
  fecha          DATE NOT NULL,
  hora_inicio    TIME NOT NULL,
  hora_fin       TIME NOT NULL,
  tipo           VARCHAR(30) NOT NULL
                 CHECK (tipo IN ('EXAMEN','RECUPERACION','PRACTICA','EVENTO','DEFENSA DE PROYECTO','DEFENSA')),
  motivo         VARCHAR(200),
  estado         VARCHAR(10) NOT NULL DEFAULT 'PENDIENTE'
                 CHECK (estado IN ('PENDIENTE','APROBADA','RECHAZADA','CANCELADA')),
  resuelto_por   INT REFERENCES usuario(id),
  observacion    VARCHAR(200),
  creado_en      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (hora_fin > hora_inicio)
);

CREATE TABLE notificacion (
  id         SERIAL PRIMARY KEY,
  usuario_id INT NOT NULL REFERENCES usuario(id),
  asunto     VARCHAR(150) NOT NULL,
  cuerpo     TEXT,
  reserva_id INT REFERENCES reserva(id) ON UPDATE CASCADE ON DELETE SET NULL,
  enviado_en TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
